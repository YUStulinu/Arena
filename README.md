# Arena

An original two-player online game with rollback netcode. Two drones duel on
a round platform that shrinks. Each can move, dash and fire a knockback
pulse, and pushes the other off the edge to win a round. First to three rounds.

| part | language | what it does |
|---|---|---|
| `engine/` | C++20 | the deterministic engine: Q16.16 fixed point only (integer sine table, integer square root), physics, the state as a plain block of integers that can be copied and hashed, and the **rollback session** (input delay, prediction of the remote input, saved states, re-simulation, stalls beyond the window, checksums of confirmed frames). It has a C interface for the server, the bots and the browser |
| `engine/scripts/arena.lua` | Lua 5.4 | the gameplay: steering, dash, pulse, cooldowns, the shrinking platform, rounds and the end of a match. It runs in a deterministic sandbox: integers only, no `pairs`, `next` or `table.sort`, no new globals, and every persistent value kept in the engine's state, so a rollback restores the script's view too |
| `server/` | Rust (standard library only) | the match server: it relays inputs over UDP (native clients, bots) and WebSocket (browsers; handshake, SHA-1 and base64 written here). It runs the confirmed frames itself in the same engine (FFI) to check the clients' checksums, ends matches and gives forfeits, and reports results |
| `matchmaker/` | Elixir/OTP | the queue, with a rating window that widens with waiting time; Glicko-2 ratings; a small HTTP API on `:gen_tcp` that also serves the browser client. Matches are created on the game server over a control port, and results come back as datagrams |
| `web/` | TypeScript | the browser client: the engine compiled to Wasm (wasi-sdk, Wasm exception handling) with a minimal WASI layer, rollback over WebSocket, Canvas drawing, keyboard controls, a practice mode and the leaderboard |
| `bots/` | Python | bots trained by self-play (PPO; opponents: itself, past checkpoints, scripted bots), a network client that plays through the server, and the tournament with Elo by maximum likelihood |
| `eval/` | Python, sh | a local match, the netem evaluation in Linux network namespaces, the online ladder with bots, the summary |

## Results

All measured numbers are in [`results/README.md`](results/README.md) (generated by `eval/summarize.py`).

### Determinism

The same replay (3000 frames of pseudo-random inputs) gives the same state hashes, `engine/tests/golden.json`, from five builds:
- g++ on Windows (MinGW) and on Linux;
- MSVC (the Rust server's build of the engine);
- clang for Wasm, in Node.

Each build's tests check this. Two sessions connected through a channel with up to 20% loss, 2–10 frames of delay and reordering agree, at every checksum, with a straight simulation of the true inputs.

### Network (netem: latency, jitter, loss)

The server and two native bot clients run in three Linux network namespaces (WSL2). netem acts on both ends of each client's link, so the latency between the clients is about twice the one-way delay. Settings: 60 frames per second, an input delay of 2 frames, a rollback window of 12 frames. Each scenario has 4 matches between a chase bot and a random bot:

| one-way delay, jitter, loss | desyncs (checksums compared) | rollbacks / min | mean / max depth | mispredicted inputs | jump at a rollback, mean / max (units) | stalls / min | up / down (bytes/s) |
|---|---|---|---|---|---|---|---|
| 0 | 0 (186) | 0 | 0 / 0 | — | 0 / 0 | 0 | 1085 / 693 |
| 20 ± 5 ms | 0 (164) | 214 | 1.4 / 3 | 10% | 0.05 / 0.91 | 0 | 1225 / 823 |
| 50 ± 10 ms, 1% | 0 (158) | 320 | 4.5 / 7 | 13% | 0.19 / 2.0 | 0 | 1448 / 1018 |
| 100 ± 20 ms, 3% | 0 (152) | 278 | 9.6 / 12 | 15% | 0.45 / 3.6 | 233 | 1783 / 1270 |
| 150 ± 40 ms, 5% | 0 (143) | 200 | 9.6 / 12 | 26% | 0.51 / 3.5 | 2808 | 1920 / 1343 |

- **No desynchronization** in any of the 20 matches, out of 803 checksums compared by the server.
- **Prediction errors.** With the remote input repeated, 10–26% of the predicted inputs turned out wrong. At a rollback a drone jumps on average 0.05–0.5 units on screen (a drone's radius is 0.5; the platform's 9).
- **Stalls.** Up to 50 ms there are none. The rollback window is 12 frames (200 ms), so beyond about 100 ms of one-way delay the client-to-client latency exceeds it and the game waits for inputs. A wider window or an input delay chosen from the measured latency would be the remedy; both are configurable, neither is automatic.
- **Bandwidth.** Under 2 KB/s up and 1.4 KB/s down per client. Inputs are one byte per frame, resent until the server acknowledges them.

The netem evaluation found two real bugs, both fixed:
- Under jitter, `START` could overtake `WELCOME`. The client ignored it and started 200 ms late, 12 frames behind its opponent, which led to constant stalls. `START` now carries the input delay itself.
- At 5% loss a `RESULT` could be lost, and a client waited until its time limit. The server now sends it again to anyone who keeps sending.

### Bots

The training was self-play PPO: 30 million decisions, 81 minutes, one RTX 2060 and 8 processes for the matches. The opponents were the learner itself (40%), past checkpoints (40%) and the scripted bots (20%). The reward was ±1 per round, plus potential-based shaping toward pushing the opponent to the edge.

The tournament (`bots/evaluate.py`) is a round robin with 40 matches per pair, both seats, 840 matches in total. Elo is fitted by maximum likelihood (Bradley-Terry):

| bot | Elo | vs chase | vs ppo_020M | vs ppo_010M |
|---|---|---|---|---|
| ppo_final (30M) | 3452 | 0.78 | 0.70 | 0.96 |
| ppo_020M | 3357 | 0.75 | — | 1.00 |
| chase (scripted) | 3136 | — | 0.25 | 0.82 |
| ppo_010M | 2873 | 0.17 | 0.00 | — |
| ppo_006M | 2763 | 0.15 | 0.00 | 0.35 |
| ppo_002M | 2495 | 0.10 | 0.00 | 0.04 |
| random | 1000 | 0.00 | 0.00 | 0.00 |

Values are points per match against the column (a draw counts 0.5). Every bot beats the random one every time, so the distance to it is set mostly by the fit's small prior. Only the differences among the other bots are informative. The policy passes the scripted bot between 10 and 20 million decisions. The final policy wins 78% against it and 70% against its own checkpoint at 20M.

### The whole system

A browser and a Python bot met through the matchmaker and played over WebSocket and UDP with rollback. The result reached the Glicko-2 ladder. `eval/ladder.py` runs the same thing with bots only.

## Building and running

```bash
engine/build.sh && engine/build/native/test_engine            # engine (Windows: MSYS2 UCRT64 first on PATH)
WASI_SDK=/path/to/wasi-sdk-34 engine/build_wasm.sh            # web/public/arena.wasm
(cd server && cargo test --release && cargo build --release)  # needs cmake
(cd matchmaker && mix test)
(cd web && npm ci && npm test && npm run build)
python -m venv .venv && .venv/Scripts/pip install torch numpy pytest
python -m pytest bots/tests
# play: the game server, the matchmaker (it serves the client on http://localhost:8080), then open the page
server/target/release/arena-server --script engine/scripts/arena.lua --report 127.0.0.1:7703 &
(cd matchmaker && ARENA_STATIC=../web mix run --no-halt)
# evaluation
python eval/local_match.py --bots chase random
sudo eval/netem.sh 4                                          # Linux, root: network namespaces + netem
python bots/train.py --steps 30000000 && python bots/evaluate.py bots/models/ppo_*.pt
python eval/ladder.py --minutes 15 random chase bots/models/ppo_final.pt
python eval/summarize.py
```

The game is original. Lua 5.4 is included unchanged in `third_party/lua` (MIT, © Lua.org, PUC-Rio).
